# Does COIA alias machinery belong in heti (shared) or stay in utina (local)?
kind: idea
tags: identifiers, architecture
created: 2026-08-13T23:18Z

- 2026-08-13T23:18Z THE QUESTION. utina implements COIA (Conventions for Opaque Identifier Aliases, ~/code/me/coia, spec in its README, coia.py is the normative oracle) to render KERI AIDs as human-friendly aliases like 9-dev-as-founder-at-acme. Built in utina 2026-08-13 because the demo needed it. Open: should it move to heti as shared machinery that utina and siblings consume?

FOR MOVING TO HETI. Aliasing is core to how people work with identifiers, not incidental to one app. Any Bakobo component that shows an AID to a human faces the same problem, and solving it once means one normalization implementation, one flag vocabulary, one set of tests against COIA's published examples. Divergent alias rendering across siblings would be its own confusion, and heti already exists to help participants prove and verify in a KERI/ACDC ecosystem, which is exactly where opaque identifiers meet people.

AGAINST MOVING. It is arguably UI-specific. COIA is explicit that an alias is creator-local and carries no security claim: it delivers human-friendliness only for the person who created it, it is 'not a commitment to meaning', and parsing someone else's aliases for strong meaning is a dangerous antipattern. Shared machinery invites exactly that misreading — a library boundary makes an alias look like a resolvable identifier rather than a private nickname. Also, the three COIA inputs (who, role, scope) are answered from application context, so a shared library can supply normalization and templates but never the answers.

WHAT WE DECIDED FOR NOW. Build in utina, deferring the question, but build so a move is cheap: keep alias construction in its own module with no dependency on utina's fold or substrate, take who/role/scope as arguments rather than reaching for them, and test against COIA's own published examples so the tests travel with the code.

CONTEXT WORTH RE-READING BEFORE DECIDING. ~/code/me/coia/README.md (the spec; note the flag vocabulary, 0 unverified, 2 pairwise, 9 test/demo, and the localization appendix which a shared library would have to carry). ~/code/me/papers/amp-diff.md section 4.3.8 (why a truncated identifier prefix must never be shown beside an alias, and why any value-derived text must come from a domain-separated digest in Crockford base32). ~/code/me/entviz-js/packages/react/docs/pill-design.md sections 2.1 and 3.3 (recognition is not verification; the pill deliberately carries no value-char teaser). The related rendering work is R-19P6 in the session of 2026-08-13.

DECIDE WHEN. Whenever a second Bakobo component needs to render an AID for a human. Before that, moving it is speculative generality; at that moment, the duplication becomes real and the answer is probably heti.

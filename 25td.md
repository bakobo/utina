# utina's pinned keripy carries the threshold-bypass: duplicate signature indices count toward a threshold
kind: debt
tags: substrate
created: 2026-09-24T15:30Z

- 2026-09-24T15:30Z Checked 2026-09-24 against the SCG handoff's native-repairs.patch. BOTH sites are unpatched in utina's pinned fork: keri/core/coring.py:4664 counts 'len(indices) >= self.thold' rather than 'len(set(indices))', so one key signing twice under two encodings satisfies an N-of-M signing threshold; keri/core/eventing.py:2894 has the same shape for witness thresholds, 'len(windices) < toader.num'.

NOT REACHABLE IN UTINA TODAY, and the reason is narrow rather than reassuring. Every AID utina incepts is single-signature and single-next-key — _SINGLE_SIG at src/utina/substrate/keripy.py:115, icount 1 isith 1 ncount 1 nsith 1 — so every threshold is 1 and one signature satisfies it legitimately. utina also configures no witnesses at all, so the second site is dead. The bug needs a threshold above 1 to bite.

So it cannot produce a wrong answer on any demo screen. It becomes live the moment utina incepts anything multisig, which is the obvious next step for a governed domain whose gAID ought not be single-key. Fix by repinning the fork onto a keripy carrying the set() repair, or by carrying the two-line patch ourselves; the upstream decision is Nicholas's and Daniel's, not utina's. See tick 4z5c, which already holds the repin question.
